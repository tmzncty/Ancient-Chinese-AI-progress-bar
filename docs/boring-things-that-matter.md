# 那些看起来很土、但真正决定古文 AI 能不能用的东西

> 一个不太严肃的“功能鄙视链反转表”。

古文 AI demo 很容易把注意力吸到模型身上：多少 B、多少上下文、会不会文言对话、能不能写诗。

真正拿去处理文献以后，经常会发现最折磨人的不是模型参数，而是一些非常没有发布会气质的东西。

## 2. 五个最容易被低估的基础设施

### 2.1 Stable IDs

作品、版本、页面、段落、实体最好都有稳定 ID。

不然今天模型告诉你：

> 《某书》第三卷第十二页。

明天数据库重新分页、换版、重新导入，链接就死了。

一个成熟系统应该能区分：

```text
work_id       作品
edition_id    版本
page_id       扫描页
region_id     页内区域
text_span_id  文本区间
entity_id     历史实体
```

这看起来不像 AI，但没有它，AI 生成的所有“出处”都很难长期引用。

---

### 2.2 Provenance graph

最好能回答这种无聊问题：

> 现在屏幕上这个字，是谁、什么时候、根据什么改成这样的？

理想状态：

```text
扫描原图
  ↓ OCR model v3.2
OCR: 「己」 confidence=0.61
  ↓ 人工校核 2026-08-28
人工: 「巳」
  ↓ 规范化层
标准字形映射: 「巳」
  ↓ 校勘层
A 本作巳 / B 本作已
```

如果最后数据库只剩一个“已”，前面发生过什么就全部消失了。

---

### 2.3 Search before chat

研究者真正高频的问题往往不是：

> “请解释这句话的哲学意义。”

而是：

> “我记得大概在宋以前，有几处把这个字这样用，给我找出来。”

这类任务最需要的是：

- 精确检索；
- 模糊检索；
- 同义 / 异体检索；
- 时间过滤；
- 文体过滤；
- 版本过滤；
- 相似句检索；
- 搜索结果回原图。

LLM 最适合站在这些工具上面，而不是替代这些工具。

---

### 2.4 Diff viewer

版本校勘最朴素、最有用的界面之一可能就是：

```diff
A 本：天命之谓性
B 本：天命之謂性
C 本：天命謂性
```

再加：

- 页图并排；
- 自动对齐；
- 差异高亮；
- 一键跳上下文；
- 模型只负责解释“这个差异可能意味着什么”。

一个好 diff viewer 的研究价值，可能高于一个会背《十三经》的聊天人格。

---

### 2.5 Abstention queue

大规模处理真正需要的不是“模型全自动”，而是：

```text
100000 条材料
  ├─ 82341 条高置信自动通过
  ├─ 12803 条低风险候选
  ├─  4217 条需要人工看一眼
  └─   639 条疑难 / 冲突 / 版本问题
```

研究者最想看的不是前 82,341 条，而是最后 4,856 条。

**AI 的价值可能不是替你判断一切，而是把异常值排到桌面最上面。**

## 3. 一些“反功能”

下面这些东西如果产品默认打开，我反而会警惕。

### 3.1 Silent normalization

OCR 完自动繁简转换、异体归并、自动改错，而且不留原值。

**问题：** 结果更干净，证据更少。

### 3.2 Helpful completion

残字看不清时，模型根据上下文帮你补一个最合理的字。

**问题：** 语言模型最擅长的事情，在底本转录阶段恰好可能是最危险的事情。

### 3.3 Citation-shaped text

输出长这样：

> 《XX》卷十二：“……”

但没有任何数据库 ID、页面、链接或可检索位置。

**问题：** 长得像 citation，不等于 citation。

### 3.4 One confidence number

> 本答案可信度：93%。

**问题：** 93% 是模型 token 概率、检索命中率、引文可靠性、校勘确信度，还是 UI 设计师心情？

更合理的是拆开：

```text
OCR confidence
retrieval score
entity-link score
citation verified: yes/no
human reviewed: yes/no
```

### 3.5 One-click “clean corpus”

把所有版本、异体、标点、注疏、页码、换行统统清成一份漂亮纯文本。

**问题：** 很适合训练，也很适合把以后可能想研究的东西提前删掉。

## 4. 最小可用古籍 AI 系统，可能长得非常不浪漫

```text
                       ┌──────────────┐
扫描图 ──► layout ──► │ 忠实 OCR 层  │
                       └──────┬───────┘
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
          原图回链        规范化索引       人工修订
              │               │               │
              └───────────────┼───────────────┘
                              ▼
                    版本化全文检索
                              │
                 ┌────────────┼────────────┐
                 ▼            ▼            ▼
              NER/RE       时间过滤      相似例句
                 │            │            │
                 └────────────┼────────────┘
                              ▼
                            LLM
                              │
                    候选解释 + 真出处
                              │
                              ▼
                          人类做决定
```

最贵的不一定是中间那个 LLM。

最难维护的也不一定是中间那个 LLM。

## 5. 一个很现实的成熟度判断

如果两个系统让我选：

### 系统 A

- 模型很大；
- 古文对话特别像；
- 输出特别漂亮；
- 经常不给出处；
- 会静默改字；
- 出错以后很难知道从哪一步开始错。

### 系统 B

- 模型普通；
- 不太会装古人；
- OCR 每字可回图；
- 每条引文可核验；
- 年代可过滤；
- 不确定时会停；
- 所有人工修改可追踪。

用于研究，我会优先选 B。

这大概也是这个仓库从 2023 到 2026 最大的变化：

> **以前我们容易问“模型能不能读古文”；现在更应该问“整个系统能不能承担一条可追溯的研究工作流”。**
